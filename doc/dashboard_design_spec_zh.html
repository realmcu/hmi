设计规格说明

本文档描述 Realtek RTL87x3G 仪表盘应用（applications/dashboard）的软件设计架构。它帮助读者快速了解仪表盘工程的整体结构、Kconfig 配置体系、GUI 移植层、UI 消息模型以及蓝牙导航投屏协议，并作为后续开发的依据。

仪表盘应用构建在 RTL87x3G SDK 之上，运行于 Zephyr RTOS，图形框架使用 HoneyGUI。它通过 RAM-less 分段刷屏驱动 SH8601Z 410×502 QSPI LCD，渲染车载风格的仪表界面：速度与功率双表盘、地图面板、媒体/歌词卡片、转向指示、LED 灯带和状态栏。蓝牙层另外提供自定义导航投屏服务，手机可以把 JPEG 地图帧推送到面板上显示。

工程分为两部分：固件是用 Zephyr 编译的纯 C 代码；而界面外观不是手写 C，而是保存在 ui_design/ 中、由 HoneyGUI 可视化设计器维护的工程，导出为 C 源码后参与编译。该目录本身是独立的 git 仓库，因此它的构建接线写在应用里，而不是它自己的 CMakeLists.txt（参见 UI 工作流）。

概述

下图给出仪表盘应用的整体框架。其中涉及三层：应用本身、port/ui/ 中的 HoneyGUI 移植层，以及其下预编译的 HoneyGUI 库和 Realtek 显示驱动。蓝牙与 GUI 是并列关系而非从属关系 —— 投屏服务负责填充帧缓冲，由 GUI 线程取用。

示例展示的内容包括：

  • 一个启动视图（dashboardMainView），带 "start engine" 按钮，用预设动画淡入，通过 Power 键进入。

  • 一个主仪表视图（dashboard_view），包含速度与功率表盘、地图面板、状态栏（时间、位置、温度、ODO、电量、音量）、六颗 LED 灯带、转向指示、弹出式应用列表和媒体卡片。

  • 一个投屏视图（carplay_view），手机推送的地图流由 hg_streaming 控件显示。

配置

仪表盘工程的功能裁剪通过 Zephyr Kconfig 完成。与依赖 F_APP_* 宏的早期 SDK 不同，本工程统一使用 CONFIG_* 形式的配置项。配置方式有两种：

  • 直接在 prj.conf 中添加或删除 CONFIG_xxx=y/n。

  • 用 west build -b rtl87x3g_evb -t menuconfig 打开字符界面的配置工具。menuconfig 是 Zephyr 的构建目标，不是 -D 变量，-DMENUCONFIG=1 在本工程不起作用。

Kconfig 层级

应用层 Kconfig 刻意保持精简。凡是决定整个子系统是否参与编译的开关，都是 Realtek 全局选项，因此写在 prj.conf 里而不是这里。应用自己的菜单只有一个 Dashboard Application，用于承载蓝牙 profile 开关：

applications/dashboard/Kconfig
├── menu 'Dashboard Application'
│   ├── config RTK_BT_BREDR            Classic Bluetooth (BR/EDR); selects BTM, SYSM, REMOTE
│   ├── config RTK_BR_PROFILE_A2DP     depends on RTK_BT_BREDR
│   ├── config RTK_BR_PROFILE_AVRCP    depends on RTK_BT_BREDR
│   ├── config RTK_BR_PROFILE_HFP      depends on RTK_BT_BREDR
│   └── config RTK_BR_PROFILE_PAN      depends on RTK_BT_BREDR
└── menu 'Zephyr Kernel'
    └── source 'Kconfig.zephyr'        Zephyr kernel config

警告

五个选项默认都是 n，而 prj.conf 把五个都设为 y。关闭 CONFIG_RTK_BT_BREDR 会连带关闭四个 profile 选项，因为它们 depends on 它。每个 profile 都会把编解码器或协议栈引入镜像，因此不需要的应当去掉。

配置分组

应用并不自造配置项：它只负责选定子系统，然后沿用各子系统自身的默认值。prj.conf 是唯一事实来源，因此本节记录的是容易搞错的决策，而不是把文件抄一遍。改任何配置之前先读 prj.conf —— 它只有 56 行，且每行都有注释。

启动序列

main() 很短并且直接返回；应用本身活在 GUI 回调和线程里。顺序很重要，因为面板、PSRAM 和 GUI 堆是分阶段建立的：

  • app_system_lower_init() —— 在 SPIC1_MEM_BASE 上建立 MPU 区域，CPU 提到 200 MHz，NOR Flash 切到 4 bit @200 MHz，两个 OPI PSRAM 分区切到 280 MHz。每一步都通过 DBG_DIRECT 打印结果。

  • 启动横幅。printf 打印板级目标，以及主线程的 id、名称和优先级。

  • gui_server_init() —— 依次执行移植钩子（gui_port_dc_init()、gui_port_indev_init()、gui_port_os_init()、gui_port_acc_init()），加载默认字体，切换帧缓冲并创建 GUI 服务端线程。

  • GUI 线程。gui_components_init() 遍历 .honeygui$init7 链接段并逐个调用注册的入口函数，dashboardEntry.c 中的 app_init() 就在这里执行：挂载 romfs、创建流传输、创建 dashboardMainView。

  • gui_set_keep_active_time(10000000) —— 把 GUI 空闲窗口从默认 5 s 拉长到 10 000 s。gui_recv_msg_to_server() 只有在超过该时长没有收到消息时才调用 gui_sleep_cb()，因此实际效果是 GUI 任务永不进入休眠、面板不会超时熄屏。

int main(void)
{
    app_system_lower_init();
    printf("Hello World! %s\n", CONFIG_BOARD_TARGET);
    printf("[main] thread id: %p, name: %s, priority: %d\n",
           k_current_get(),
           k_thread_name_get(k_current_get()),
           k_thread_priority_get(k_current_get()));

    gui_server_init();
    gui_set_keep_active_time(10000000);
    return 0;
}

底层初始化

app_system_lower_init() 在任何内存分配发生之前配置好存储系统。MPU 区域覆盖 SPIC1_MEM_BASE（0x22000000）处 4 MB 的可缓存、可写、可执行窗口，GUI 帧正是从这里读取的：

uint32_t mpu_cfg_rbar = SPIC1_MEM_BASE | (1 << 1);   /* SH:0, AP:1, XN:0 */
uint32_t limit_addr   = SPIC1_MEM_BASE + 0x400000;  /* PXN:0, EN:1  */
mpu_set_region(mpu_cfg_rbar, limit_addr, 2, 0x44, true);

说明

SPIC1 既是 LCD 流水线使用的可缓存窗口，也是投屏帧槽位的所在；SPIC3 则承载 GUI 大对象堆。把两者分开，才使得 gui_port_os.c 可以保留 SPIC3 起始的 512 KB 而不影响显示通路。

初始化与注册机制

本应用没有自己的模块注册表。它依赖 HoneyGUI 提供的链接段，以及 main() 中的直接函数调用：

/* ui_design/src/dashboardEntry.c */
static int app_init(void)
{
#ifdef _HONEYGUI_SIMULATOR_
    gui_vfs_mount_posix("/", "./assets");
#else
    gui_vfs_mount_romfs("/", (void *)0x704D1400, 0);
#endif

    /* @protected start app_init_pre */
    extern int app_stream_transport_init(void);
    app_stream_transport_init();
    /* @protected end app_init_pre */

    gui_view_create(gui_obj_get_root(), "dashboardMainView", 0, 0, 0, 0);
    return 0;
}
GUI_INIT_APP_EXPORT(app_init);

GUI_INIT_APP_EXPORT() 把 app_init 的指针放进 .honeygui$init7 段；gui_components_init() 遍历 __honeygui_init_app_init_start 到 __honeygui_init_app_init_end，依次调用每个入口。这也解释了为什么两个 app_init 定义不能共存：符号名由函数名生成，第二个会变成链接错误，而不是运行期的意外。

@protected 标记由设计器保留：标记之间的代码在重新导出后仍然存在，标记之外的内容会被重新生成。所有手工改动都必须写在保护块内，否则下一次导出会把它悄悄删掉。

动画框架

大部分动效来自 HML 中定义的预设时间线：一个固定间隔的定时器、一组片段，以及每个片段对应的动作（透明度、位置、可见性、缩放）。生成的 *_timer_N_cb 于是只需触发边界动作，这正是 preset_anim_boundary_crossed() 的用途：

static bool preset_anim_boundary_crossed(uint32_t at_ms, uint32_t prev_ms,
                                         uint32_t now_ms, bool cycle_wrapped, bool cycle_skipped)
{
    if (cycle_skipped) return true;                                  /* a whole cycle elapsed */
    if (cycle_wrapped) return (at_ms > prev_ms) || (at_ms <= now_ms); /* boundary inside the wrap */
    return (at_ms > prev_ms) && (at_ms <= now_ms);
}

每个带动画的控件都保留三个变量（_timer_start_ms、_started、_prev_elapsed_ms），与 gui_ms_get() 比较。这样一个片段动作在每次进入该片段时恰好执行一次，即使 GUI 线程跳帧或定时器被重启 —— 之所以需要这道保护，是因为这些定时器由渲染循环驱动，而不是硬件定时器。

dashboard_entrance_timer_0_cb() 是扇出点：仪表视图可见后 1 秒，它启动地图、表盘、LED 和文本等 19 个定时器。它还会检查当前视图是否已经是 carplay_view，如果是，就跳过入场动画、只启动地图与速度/功率文本定时器，从而避免从投屏返回时重放一遍入场效果。

UI 工作流

重新生成 UI 是两步操作，第二步很容易忘：

  • 在设计器里修改 ui/DashboardMain.hml 与资源，然后导出。设计器会重写 src/（保留 @protected 块）并重建 ui_design/build/ 下的 romfs。

  • 重新烧录 romfs 区域。west build 只编译生成的 C 代码，从不更新资源区，因此在把 app_romfs.bin 写到 0x704D1400 之前，面板会一直显示旧图片（参见 编译与烧录）。

全新克隆通常根本没有 ui_design/src，因为该目录在仪表盘仓库里未跟踪。此时构建会打印 ui_design: no generated sources ... UI will not be built，固件启动后是一个空的根节点 —— 不是崩溃，只是黑屏。

蓝牙连接

仪表盘是一个低功耗蓝牙外设。它以 BLE_NAVI 为名广播，提供标准的电池服务、simple-BLE 服务以及一个自定义导航投屏服务，并允许手机把 JPEG 地图帧推进 PSRAM 供投屏视图使用。经典蓝牙（BR/EDR）在 prj.conf 中也已打开，但本应用还没有任何 profile 模块用到它。

协议栈启动

BLE 侧的逻辑跑在单个 Zephyr 线程上。ble_task.c 创建两个 Realtek ROM 消息队列并交给 gap_start_bt_stack()，真正启动协议栈的是后者：

#define BLE_TASK_PRIORITY           5
#define BLE_TASK_STACK_SIZE         4096
#define MAX_NUMBER_OF_GAP_MESSAGE   0x20
#define MAX_NUMBER_OF_IO_MESSAGE    0x20
#define MAX_NUMBER_OF_EVENT_MESSAGE (MAX_NUMBER_OF_GAP_MESSAGE + MAX_NUMBER_OF_IO_MESSAGE)

static void ble_thread_func(void *p1, void *p2, void *p3)
{
    os_msg_queue_create(&io_queue_handle,  "ioQ",  MAX_NUMBER_OF_IO_MESSAGE,  sizeof(T_IO_MSG));
    os_msg_queue_create(&evt_queue_handle, "evtQ", MAX_NUMBER_OF_EVENT_MESSAGE, sizeof(uint8_t));

    gap_start_bt_stack(evt_queue_handle, io_queue_handle, MAX_NUMBER_OF_GAP_MESSAGE);

    while (1)
    {
        if (os_msg_recv(evt_queue_handle, &event, 0xFFFFFFFF) == true)
        {
            if (event == EVENT_IO_TO_APP)
            {
                T_IO_MSG io_msg;
                if (os_msg_recv(io_queue_handle, &io_msg, 0) == true)
                {
                    app_ble_gap_handle_io_msg(io_msg);
                }
            }
            else
            {
                gap_handle_msg(event);
            }
        }
    }
}

事件队列创建 64 个槽位（MAX_NUMBER_OF_GAP_MESSAGE + MAX_NUMBER_OF_IO_MESSAGE），gap_start_bt_stack() 的第三个参数传入 32，作为 msg_queue_elem_num，即协议栈可占用的队列元素数。应用载荷走独立的 IO 队列，因此等待应用处理的数据不会挤占 GAP 事件所用的队列。

警告

有三个函数没有调用者：app_ble_gap_init()、app_ble_service_init() 和 ble_task_init()。代码参与编译和链接，但协议栈从未启动。接入清单 给出了正确顺序。

导航投屏协议

协议分两层。L1 是轻量成帧层，加上同步字节、控制字段、长度、CRC 和序列号。L2 是命令层，承载会话的 OPEN/ACK/CLOSE 交互，以及帧、信用和上报流量。

一次完整的会话按下图的顺序进行。字节布局随后给出，但不要试图从布局反推流程。

L1 frame (control channel, 0xFFD1 write / 0xFFD2 notify)
  +--------+--------+---------+----------+---------+-------------+
  | 0xAB   | ctrl   | len BE  | crc16 BE | seq BE  | payload ... |

NAVI_MIN_PACKET 正是由上报长度反推出来的：L2 头 5 字节，加上序列号与计数 3 字节，再加 16 段 × 6 字节，正好 104 字节 —— 这就是手机不能协商更小包长的原因。

信用流控

手机发送的包数不能超过设备授予的信用，而设备按包授权，不按字节。以协商 244 字节包长为例：

first          = max_packet - 12                        /* 232 */
pkt            = max_packet - 8                         /* 236 */
frame_credits  = 1 + ceil((131072 - first) / pkt)       /* 556 */
total_credit   = frame_credits * 3                      /* 1668, three slots */

每收到一个包消耗一份信用。帧接收完成或被丢弃时，已消耗的信用通过 CREDIT 通知归还 —— 失败路径同样如此：CRC 不匹配或解码失败时也会先归还信用，再回收槽位。手机信用耗尽后必须停下等待；设备会丢弃无信用到达的包并计数（FRAME received but no credit, dropped）。

会话状态机

OPEN 在状态切换之前完成校验：载荷至少 11 字节，protocol_version 必须为 0x02，两个必需特性位（RAW_ATT_PACKET 与 FRAME_CRC32）必须置位，流控必须使能，max_packet 落在 104–244，宽高 1–1024，fps 1–30。校验失败回 NAVI_RESULT_UNSUPPORTED，已有活动会话回 NAVI_RESULT_BUSY，PSRAM 分配失败回 NAVI_RESULT_LOW_MEMORY。

说明

navi_state_t 声明了三个取值 —— NAVI_STATE_IDLE、NAVI_STATE_VALIDATING 和 NAVI_STATE_ACTIVE —— 但实现从未进入 NAVI_STATE_VALIDATING：校验失败会在改动状态之前返回，因此客户端只可能观察到 IDLE 或 ACTIVE。

帧重组与三重缓冲

帧很大（最大 128 KB），且重传导致分包乱序到达，因此每个槽位维护一张已收字节位图，每字节一位（每个槽位 16 KB）。当终止包到达且位图没有空洞时，帧才算完整；空洞会通过上报告知手机，手机只重发这些区间。

  • 定位槽位。navi_find_slot() 先按 frame_seq 匹配已有的 RECEIVING 槽位，否则取第一个 FREE 槽位。三个槽位是最低要求：一个在显示、一个已就绪、一个在填充。

  • 记账并拷贝。每个收到的字节都在 chunk_bitmap 中标记，只有此前未标记的字节才消耗信用。数据拷贝到 jpeg_buffer + 16 + offset，前 16 字节留给 HoneyGUI 图像头。

  • 检测尾包。满足 offset + length == total_len 的包会置位 terminal_seen，随后扫描位图查找空洞。

  • 上报或完成。最多 16 段空洞通过 REPORT 发出，并归还待归还的信用；没有空洞则进入校验。

  • 校验。对 JPEG 本体（不含 16 字节头）计算 CRC32（IEEE，初值/结果异或 0xFFFFFFFF），再检查 FF D8 … FF D9 标记，最后调用 SCB_CleanDCache_by_Addr() 确保 GUI 与 JPU 从 PSRAM 读到一致数据。

  • 发布。就绪槽位置为 READY 并投递一条 GUI_EVENT_USER_DEFINE 消息。如果旧的 READY 槽位一直没被取走，它会被回收并计入 s_perf_ready_drops。

  • 取用。在 GUI 线程中，navi_gui_consume_ready() 调用已安装的 GUI 回调；新帧被接受后，原先 USE 的槽位立即回到 FREE，这就是"最新帧优先"规则。

三个槽位取自 SPIC1_MEM_BASE 处一块固定的 512 KB 窗口 —— 也正是 MPU 配置覆盖的可缓存区域 —— 因此接收过程从不在 BLE 回调里分配内存。三块 128 KB + 16 B 的 JPEG 缓冲加三块 16 KB 位图共需 442,416 字节，这个数字决定了池子的大小。

之所以有两个回调，是因为两类消费者需求不同。navi_frame_ready_cb_t 在 BLE 线程运行，收到的是裸 JPEG；navi_gui_frame_cb_t 在 GUI 线程运行，收到的是含 16 字节 HoneyGUI 头的同一块缓冲，可以直接交给流控件而无需再拷贝一次。头部由服务本身填写：jpeg = 1、type = 12、OPEN 协商的宽高，偏移 8 处是 JPEG 长度。

接入清单

服务、协议和缓冲都已完备，缺的是接线。按顺序完成以下步骤，即可把已编译的代码变成可用的投屏链路：

  • 启动协议栈。在 main() 中、app_system_lower_init() 之后依次调用 app_ble_gap_init()、app_ble_service_init()，最后调用 ble_task_init()。顺序是固定的：真正调用 gap_start_bt_stack() 的是 ble_task_init()，因此 GAP 与 GATT 服务必须已经注册。

  • 给服务一个消费者。用 navi_projection_set_gui_frame_cb() 安装 GUI 侧回调（示例见下），它收到的缓冲已包含 16 字节 HoneyGUI 头；或改用 BLE 线程侧的 navi_projection_set_frame_cb()，它收到裸 JPEG，由你自行封装。

  • 对齐缓冲大小。流传输按 35 KB 帧配置，而协议允许 128 KB。把 APP_STREAM_MAX_FRAME 提到 128 * 1024 + 16，同时相应降低 APP_STREAM_BUF_COUNT —— 32 × 35 KB 已经是 1.1 MB，必须降低环深才能留在 PSRAM 预算内。

  • 断链时关闭会话。在 app_ble_gap_handle_conn_state_evt() 的 GAP_CONN_STATE_DISCONNECTED 分支里补上 navi_projection_close()。否则状态会停在 ACTIVE，下一次 OPEN 会被回以 BUSY。

  • 由手机侧提升 MTU。设备从不主动发起交换，因此配套 App 必须请求 247；否则 max_packet 偏小，信用算法会算出多得多的分包数。

  • 可选：用已定义的 NAVI_SESSION_TIMEOUT_MS（10 s）配合 s_last_data_time_ms 实现会话看门狗，避免手机卡死时三个槽位被永久占用。

第二步中 GUI 侧回调的写法如下：

static bool gui_push(const uint8_t *p_gui_src, uint32_t jpeg_len, uint16_t seq)
{
    /* p_gui_src already carries the 16-byte HoneyGUI header */
    return app_stream_push(p_gui_src, jpeg_len + 16, seq);

Realtek 日志通路

src/system/rtk_log_backend.c 是一个 Zephyr 日志后端，把每条记录交给 Realtek 的日志通道 —— 也就是 DBG_DIRECT() 写的那一条：

LOG_*() / printk()
    -> 日志子系统（延迟模式）-> 日志线程
    -> rtk_log_backend：格式化成一行 -> DBG_DIRECT("%s", line)
    -> ROM log_direct() -> Realtek trace 通道 -> 调试分析仪

这套链路能在崩溃时工作，靠的是四点：

  • ROM 那个接口是 printf 风格的，所以先格式化进 200 字节的 RAM 行缓冲，按行发送，而不是按字符。

  • 通道是轮询输出，因此在故障处理函数里照样能用 —— 模式 A/C 下的寄存器转储和 coredump 就是这么送到分析仪的。

  • 后端实现了 panic 回调，LOG_PANIC() 会先把队列里积压的记录排空，崩溃前最后几条不会丢。

  • printf() 被重定向到同一条通道（见下），应用里的打印跟着同一个开关走，不会出现"日志跑一边、printf 跑另一边"。

日志线程跑在优先级 1，每条记录都会唤醒（CONFIG_LOG_PROCESS_TRIGGER_THRESHOLD=1），所以延迟输出不会被压在 4 KB 缓冲的尾部。

CONFIG_RTK_LOG_BACKEND 定义在应用的 Kconfig 里。关掉它是干净的移除：没有后端、没有 printf 覆盖、也没有死代码。

抓一次崩溃

CONFIG_FAULT_DUMP=2 下，ARM 故障处理函数会用 LOG_ERR 输出寄存器组、出错指令地址和当前线程，所以它同样遵循上面选的去向。想连 coredump 一起拿到，再加这四个选项：

CONFIG_DEBUG_COREDUMP=y
CONFIG_DEBUG_COREDUMP_BACKEND_LOGGING=y
CONFIG_DEBUG_COREDUMP_MEMORY_DUMP_MIN=y
CONFIG_EXTRA_EXCEPTION_INFO=y

MEMORY_DUMP_MIN 只转储出错线程的 k_thread 结构和它的栈。这段数据以十六进制编码夹在 #CD:BEGIN# 与 #CD:END# 之间，每行 16 字节 —— 它是给工具解的不是给人读的：

python zephyr/scripts/coredump/coredump_serial_log_parser.py crash.log coredump.bin
python zephyr/scripts/coredump/coredump_gdbserver.py build/zephyr/zephyr.elf coredump.bin --port 1234
arm-none-eabi-gdb build/zephyr/zephyr.elf -ex "target remote localhost:1234"

这样 bt 出来的是带文件名和行号的调用栈，因为栈内容被一起抓下来了。日志前缀不会干扰解析：parser 在整行里找 #CD:。

另外两段没人配置的转储

SDK 修改了默认的 k_sys_fatal_error_handler（zephyr/kernel/fatal.c），在停机前调用 ROM 的 dump_log_buffer() 和 dump_raw_memory_all()。这段输出与日志模式无关，出现在 #CD:END# 之后。

问题排查

  • 黑屏并伴随资源断言。资源区从未烧录。west build 不会更新它，把 app_romfs.bin 烧到 0x704D1400。

  • 黑屏且根节点为空。ui_design/src 缺失，应用在没有任何 UI 的情况下编译完成。构建会打印 ui_design: no generated sources ... UI will not be built，先导出工程。

  • 链接错误：__honeygui_init_app_init 重复定义。某个 CONFIG_REALTEK_BUILD_EXAMPLE_*_WIDGET 选项被打开。app_init() 只能由应用拥有。

  • 设备不广播。ble_task_init() 尚未被调用，BLE 协议栈从未启动。参见 接入清单。

  • 会话建立但地图不刷新。要么帧回调是 NULL（两个回调默认都未设置），要么 JPEG 大于 APP_STREAM_MAX_FRAME（35 KB）。

  • 第二次 OPEN 被回以 BUSY。上一次会话没有在断链时关闭；在断链处理里补上 navi_projection_close()。

  • port/flashdb 与 port/posix 打印 skip。这是预期行为：本源码树中没有 component/FlashDB 和 component/posix，两个移植层会提前返回。因此 shell 里也没有 fdb 命令。

  • 控制台无声。先确认波特率：overlay 把 uart2 固定在 P1_1/P1_0，2000000 波特率，而 P1_1/P1_0 同时也是 SWD 引脚对。overlay 里的注释块记录了试过的其他引脚。

  • 某个按键无反应。它的设备树节点是 status = "disabled"，或标签与回调文件中的 strcmp 目标不匹配。
