1. Project Overview

RustMcuClaw is an AI agent watch whose business core is written in Rust and runs on the RTL8783G + AmebaZ2+ dual-chip architecture. The MCU handles the UI, control flow, file system, and scheduled tasks, while Z2Plus acts as the wireless co-processor for all network services such as Wi-Fi/HTTPS/WebSocket.

Design Goals

  • Memory safety: business logic in Rust, using unsafe only at the FFI/allocator/C-string boundaries
  • Dual-chip decoupling: the MCU never touches any TCP/TLS stack; Z2Plus is controlled via AT commands
  • Pluggable cloud LLM: OpenAI / Kimi / GitHub Models / OpenAI-Compatible
  • Persistence: persona, summary memory, and tasks all stored on the SD card FatFS
  • Proactive interaction: Feishu wss long-connection push → straight into the LLM channel

Key Components

  • MCU Zephyr multithreading + Rust static library
  • Z2Plus AT firmware (ATPN/ATWT/ATKM/ATEP/ATFS/ATSD)
  • LLM the rustmcuclaw-mcu crate generates OpenAI-compatible JSON
  • UART uart2 CLI · uart3 ↔ Z2Plus AT channel
  • UI SH8601Z QSPI LCD + CHSC6417 touch + GNU Unifont
  • Memory PSRAM bump allocator + FatFS on SD

★ Agent Loop (user input · prompt · ToolCall · Loop · files)

RustMcuClaw's "brain" is a standard Agent main loop: it assembles the user input together with the persona/memory/tasks into a prompt and calls the LLM; if the response contains a tool call, it executes it locally and feeds the result back, iterating at most max_tool_loops times; after producing the final reply it asynchronously generates a summary of at most 50 characters and persists it.

Prompt assembly order

  1. soul.md — assistant core persona
  2. role.md — behavior/boundary constraints
  3. user.md — user profile
  4. latest N summary — long-term memory
  5. latest history_limit rounds of dialogue
  6. current user input

Tool capabilities

  • task.add / list / done — period ≥ 10 min
  • fs.read / write — restricted to /SD:/RustMcuClaw
  • time.now — wall_clock_base + uptime
  • feishu.reply — reply via the ATFS channel
  • call results are fed back into messages[] with the tool role

3. MCU Side (RTL87x3G) Software Architecture

Zephyr RTOS runs on the MCU. Every "blocking" job occupies its own thread and never preempts the main chat path. The Rust library is called concurrently from several threads through a few entry functions exposed via extern "C", and brings its own k_mutex serialization.

Key mutexes

  • claw_lock: protects the Rust global context so the cli / poll / urc threads serialize on the same LLM context
  • z2_uart_lock: ensures an AT command-response pair on uart3 is not interleaved by another thread's command
  • display_lock: mutex between the animation work and cli framebuffer rendering

4. Z2Plus (AmebaZ2+) Co-processor

Z2Plus runs its own AT firmware and is RustMcuClaw's only "network egress". The MCU implements neither Wi-Fi nor TLS; everything is delegated to Z2Plus and invoked in a controlled way through a set of AT commands + URC.

Design tradeoffs

  • ATKM keeps Kimi authentication on the Z2 side; the MCU sends only the prompt → significantly reduces MCU transfer/memory load
  • Generic HTTPS POST as a fallback: the OpenAI-Compatible JSON generated by Rust is passed through to Z2
  • Feishu URC is wrapped in text marker blocks to avoid fragment mis-parsing
  • On failure it returns ret=X http=Y, from which the MCU distinguishes local/network/service errors

5. UART Bridge (MCU ↔ Z2Plus)

The two UARTs each serve a purpose: uart2 is exposed to a PC terminal for debugging and user conversation; uart3 is the bidirectional synchronous-AT + asynchronous-URC channel between the MCU and Z2Plus.

uart2 (CLI / Console)

  • IRQ-driven + 2048-byte msgq
  • supports \r/\n line endings, automatically drops empty lines
  • optional local echo (CLI_LOCAL_ECHO)

uart3 (Z2Plus AT)

  • also IRQ + msgq, dedicated to communication with Z2
  • large JSON fragment transfer: throttle 30 ms per 1024 B to avoid Z2 overflow
  • JSON parser: tracks depth/escapes character by character in uart_read_json_body
  • z2_uart_lock guarantees atomic AT command-response pairing

6. HTTPS and LLM Calls

The Rust crate abstracts LLM requests as a Provider, ultimately landing on a single "transparent HTTPS POST". The MCU does not own TLS; it just hands the endpoint / header / body to Z2Plus, which completes the TLS handshake and returns the raw response.

  • timeout 190 s leaves enough thinking time for the LLM

7. Feishu WebSocket Long Connection

To achieve "passive wake-up", Z2Plus maintains a wss long connection to the Feishu Open Platform; any Feishu event is packed into a text-block URC pushed to uart3, then reassembled by the MCU's z2_urc thread and handed to Rust, which automatically enters the LLM channel and pushes the answer back to Feishu.

fill the 12 KB fsev_buf URC->>RUST: rustmcuclaw_mcu_handle_feishu_event(buf,len) RUST->>RUST: parse sender / chat_id / text RUST->>RUST: trigger a normal LLM round RUST->>U3: HTTPS POST → Feishu reply U3->>FS: reply via the ATFS channel RUST->>U2: also show locally on the LCD end

URC text protocol

\r\n[FSEV-BEGIN]\r\n
type: message_received\r\n
chat_id: oc_xxx\r\n
\r\n
{"sender":"...","text":"Good morning"}\r\n
[FSEV-END]\r\n
  • dedicated-priority thread to avoid lock contention with the CLI starving replies
  • FSEV_BUF_MAX = 12 KB; oversized events are truncated with a warning

Dual-channel fusion

  • Feishu events and CLI input both feed into the same app::handle_line
  • share the same memory / soul / role / tasks
  • the LCD title color uses DISPLAY_COL_SYSTEM to distinguish the push source

8. Memory and PSRAM Layout

The MCU's SRAM is tight, so all large buffers and the Rust heap are moved to the 4 MB PSRAM. Rust uses a simple bump allocator to fit no_std + alloc, and proactively reinitializes when the heap watermark is too high to avoid long-run fragmentation.

Rust allocator

  • rustmcuclaw_mcu_init() takes (base, size)
  • implements GlobalAlloc: bump + free-list fallback
  • when the heap is 70% full, claw_poll triggers reinit during idle periods
  • all large String / Vec / serde JSON buffers live here

SD card data directory

  • mount point /SD:, FatFS goes directly through DISK_ACCESS
  • path format is identical to the PC version, convenient for offline editing
  • writes the default rmcc.toml on first boot
  • the Unifont binary is generated offline by tools/gen_unifont_bin.py
